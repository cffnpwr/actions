# ADR-0006: check-version-consistency への Result 型導入

## コンテキスト

現在の実装では、`NixProvider`・`MiseProvider`のエラーは`RuntimeError`を`raise`する例外ベースの設計である。
`main.py`はこれらの例外を一切`try/except`していないため、エラー発生時はトレースバック付きで異常終了する。

例外ベースの設計には以下の問題がある。

- エラーの可能性が型シグネチャに現れないため、呼び出し側は例外が起きうることを型情報から知る手段がない
- 呼び出した関数がどの例外型を投げるかは実装を読まないとわからず、`try/except`のキャッチ対象を誤りやすい
- `NixProvider`・`MiseProvider`が投げるエラーは「外部コマンドが失敗した」という想定内の失敗であり、例外（想定外の事象）として表現するのは意味的に不正確である

Result型を導入することで、想定内の失敗を型シグネチャで明示し、呼び出し側に展開を強制できる。
`returns`ライブラリはすでに`pyproject.toml`の依存関係に含まれている。

## 検討した選択肢

### 選択肢1: 導入しない（現状維持）

例外ベースの設計を維持する。`main.py`に`try/except`を追加してエラーメッセージを整形する対応のみを行う。

#### 良い点

- コード変更が最小限（`main.py`のみ）
- テストコードの変更が不要
- Pythonの慣用的なスタイルから外れない
- `**kwargs`でソースを受け取る`check_consistency()`のシグネチャをそのまま維持できる

#### 悪い点

- エラーの可能性が型シグネチャに現れないため、新しいプロバイダを追加した際に`main.py`のエラーハンドリング漏れを型チェッカーが検出できない
- キャッチすべき例外型が型情報からわからず、`try/except`のキャッチ対象を誤るリスクがある
- 想定内の失敗を例外として表現することになり、意味的に不正確である

### 選択肢2: Result 型を導入する（`returns`ライブラリ）

`fetch_tool_versions()`の戻り値を`ResultE[dict[str, str]]`（= `Result[dict[str, str], Exception]`）に変更する。
コンストラクタでのバイナリ解決失敗は、`create()` classmethodによる生成パターンに変更する。

#### 良い点

- 想定内の失敗が型シグネチャに現れ、意味的に正確な設計になる
- Result型を展開せずに使おうとすると型エラーになるため、ハンドリング漏れを型チェッカーが検出できる
- `main.py`で`match`文による網羅的なハンドリングが書ける

#### 悪い点

- 変更範囲が広い（`base.py`・`nix.py`・`mise.py`・`checker.py`・`main.py`および全テストファイル）
- コンストラクタを`create()` classmethodに変更すると、プロバイダの生成コードが変わり`main.py`の変更も大きくなる
- `**kwargs`で`ResultE[dict[str, str]]`を受け取る`check_consistency()`のシグネチャはPythonの型システム上扱いにくい。
  `main.py`側でResultを展開してから渡す設計に変える必要がある
- `returns`ライブラリのAPIはPythonの標準的なスタイルと異なるため、コードの読み手に学習コストが生じる
- テストコードの`pytest.raises`パターンをすべてResult型のアサーションに書き直す必要がある

## 決定

選択肢2（Result型導入）を採用する。

`NixProvider`・`MiseProvider`が投げるエラーは想定内の失敗であり、例外ではなくResult型の`Err`として表現することが意味的に正確である。
また、Result型を展開しないと型エラーになるため、`try/except`では得られないハンドリング漏れの検出が型チェッカーで行える点が決め手となった。
変更範囲は広いが一時的なコストであり、設計の正確さと長期的な保守性が上回る。

## 結果

### 良い影響

- 想定内の失敗がResult型で表現され、設計の意図が型シグネチャに現れる
- Result型の展開忘れを型チェッカーが検出できるため、新しいプロバイダを追加した際のハンドリング漏れを防げる
- `main.py`のエラーハンドリングが`match`文で網羅的に記述でき、可読性が上がる

### 悪い影響

- 実装ファイル・テストファイルを含む広範な変更が必要になる
- `returns`ライブラリのAPIに習熟していない開発者には学習コストが生じる
