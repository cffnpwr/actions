# ADR-0004: check-version-consistency の CLI ライブラリ選択

## コンテキスト

ADR-0003にて、check-version-consistencyの実装言語としてPythonを採用することを決定した。
本ADRではエントリポイントのCLIインターフェース実装に使用するライブラリを決定する。

CLIが受け取る引数は以下の通り。

- `--flake-dir`: Nix flakeのディレクトリパス
- `--project-dir`: miseプロジェクトのディレクトリパス

## 検討した選択肢

### 選択肢1: argparse（stdlib）

Pythonの標準ライブラリに含まれるCLIパーサ。

#### 良い点

- 追加依存なし（stdlib）
- `pyproject.toml`の変更不要
- `uv.lock`の更新不要

#### 悪い点

- 型アノテーションとの統合が薄く、型安全性が低い
- ボイラープレートが多い

### 選択肢2: click

Pallettsが開発するサードパーティCLIライブラリ。デコレータベースのAPI。

#### 良い点

- デコレータベースで記述が簡潔
- エラーメッセージが充実している
- 広く使われており実績がある

#### 悪い点

- 外部依存が追加される（`pyproject.toml`・`uv.lock`の変更が必要）
- Pydanticとの型統合がなく、型アノテーションは別途必要

### 選択肢3: typer

clickをベースにしたサードパーティCLIライブラリ。型アノテーションからCLIを生成する。

#### 良い点

- 型アノテーションからCLIを自動生成し、型安全性が高い
- Pydanticとの親和性が高い
- 記述量が少ない

#### 悪い点

- 外部依存が追加される（`pyproject.toml`・`uv.lock`の変更が必要）
- clickに依存するため、間接依存も増える

## 決定

選択肢3（typer）を採用する。

このツールはすでにPydanticを依存に持つため、typerのPydanticとの高い親和性が活かせる。
引数の型アノテーションからCLIを自動生成する設計は、型安全性と記述量の両面で他の選択肢より優れる。
外部依存が増えるデメリットはあるが、pydanticをすでに採用している以上、追加依存のコストは限定的である。

## 結果

### 良い影響

- 型アノテーションからCLIを自動生成するため、実装量を減らしつつ型安全性を高められる
- Pydanticとの親和性が高く、既存モデルとの統合がしやすい

### 悪い影響

- 外部依存が追加される（typer・clickの2パッケージが`pyproject.toml`と`uv.lock`に追加される）
